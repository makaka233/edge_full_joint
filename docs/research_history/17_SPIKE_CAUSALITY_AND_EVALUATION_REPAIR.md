# Agent-D 负向尖峰的因果归类、物理模型审查和评价修复（2026-11-19）

## 结论（严格区分三类问题）

**已确认：部分严重负尖峰来自当前定义下结构合法、却在平均需求下不可能持续承载 CPU 的完整部署。** 当前环境的 `Env.legal()/Env.commit()` 只检查阶段覆盖、RAM 和 SSD，不检验计算需求是否可能被可用副本承载。**已确认：6 秒预热 + 每窗口独立空队列的短窗评价会漏报这类不可持续部署。** **已确认：`failed` 实为观察尾部结束时的未完成/截尾请求，并不等同于实际丢弃；固定每个截尾请求 10 秒惩罚使负峰进一步变大。**

**尚未确认：底层事件引擎存在错误、需要完全禁止 CPU 高风险动作、或当前修复已使 Agent-D 收敛。** 对六个持续物理案例，资源速率容量误差与工作量守恒误差均在数值精度范围。RL 未通过长期稳定学习证明。

## 1. 根因证据：192 条全部原始训练轨迹（无删除）

从 `hierarchical_results/train.jsonl` 取全部 192 条（原扁平和阶段→节点各 96 条），用记录中的 `matrix_packed_hex` 恢复实际 28×32 矩阵，对每个完整矩阵求解理想 CPU min-max 线性规划：

\[
\rho^*(X)=\min_{z\ge0,\rho}\rho,\quad
\sum_{n:X_{kn}=1}z_{kn}=D_k,\quad
\sum_k z_{kn}\le \rho C_n .
\]

其中 \(D_k\) 是当前场景长期平均阶段 CPU 工作量到达速率，\(C_n\) 为节点 CPU 容量。此结果是**必要可行性证据，不是实际调度 E2E 预测**。即使 \(\rho^*<1\)，调度、路径传输、到达突发、无线竞争也可能使有限时延不达标。

| 条件 | 样本数 | 短窗中至少一条请求截尾 |
|---|---:|---:|
| 通过阶段覆盖 / RAM / SSD 检查 | 192 | 19 |
| 理想 CPU 负载下界 ≥ 1 | **34** | 19 |
| 理想 CPU 负载下界 ≥ 1，短窗却无截尾 | **15** | 0 |
| 理想 CPU 负载下界 < 1 | 158 | 0 |

这是来源于已存真实训练矩阵的全量重算，而非通过 Reward 选取的训练动作。样本局限于既有种子/需求世界，不能把「\(\rho^*<1\) 的短窗无截尾」推广到一般必然安全。

**重要修正**：既有 `cpu_stage_pair_bound` 只检查单阶段、两阶段及总量下界，可能低估需要三阶段以上联合瓶颈的真实 \(\rho^*\)。例如一条记录的旧下界为 0.8719，但精确 LP 为 1.2287，实际已有 16 个截尾请求。不能仅凭这个较弱的下界宣称 CPU 没有过载。

完整逐行结果：`spike_causality_results/all_192_exact_lp.json`；复现：`python audit_spike_classification.py`。

## 3. 持续 120s 同请求流：短窗假安全的实际后果

`audit_sustained_physics.py` 使用原 Simulator 连续推进长请求流，使用每个 6s cohort 相同的 8s 观察尾部统计延迟/截尾。关键案例：

| Seed / 场景 / 部署 | \(\rho^*\) | 短窗截尾 | 120s 流内尾部截尾 / 请求数 | 截尾请求后续完成 | 120s+尾部仍未完成 |
|---|---:|---:|---:|---:|---:|
| 14 / 56 / 严重过载 | 3.5416 | 167 | 2205 / 4005 | 275 | 1930 |
| 14 / 56 / **假安全** | **1.1566** | **0** | **794 / 4005** | **556** | **238** |
| 14 / 56 / 承载充分 | 0.4451 | 0 | 0 / 4005 | 0 | 0 |
| 13 / 35 / 边界 | 0.9680 | 0 | 173 / 2204 | 168 | 5 |

注意：`failed` 是**超过指定 cohort 8 秒尾部时仍未完成**，不是网络实际上丢弃 794 个请求。Seed14 假安全部署中 556 个尾部截尾请求在稍后的持续仿真内完成。因而当前报告和日志的 `failed` 必须明确注释为 `tail_censored`，不能把它当作永久业务失败率。

这六条物理重放的 `max_capacity_error` 约 ≤5.7e-14，`max_work_conservation_error` ≤2.7e-10，未显示明显的资源速率越限/创造额外计算量错误。这不是对整个仿真正确性的形式证明。

数据：`spike_sustained_physics.json`，复现：`python audit_sustained_physics.py`。

## 4. 负向尖峰有多少是固定 10 秒惩罚？

原 Reward 不变：`Reward = -[10 * (观测时延下界之和 + 10s * 尾部截尾数)/总 cohort 请求数 + 持有成本 + 切换成本]`。以 Seed14 Scene56 最差部署为例：

- 原始 Reward -102.4713；167 / 381 尾部截尾；
- 10 秒/截尾请求引起的 Reward 成分 `-10 * 10 * 167 / 381 = -43.8320`；
- 扣除**该惩罚成分**后的 Reward 仍为 **-58.6393**，远低于同场景承载充分布局的 -5.6846。

因此，单纯降低/裁剪失败惩罚既会改变研究目标，又无法解决真实严重积压。原评价**将尾部截尾误称为永久失败**是语义缺陷；固定惩罚本身应作为显式时延/服务等级合同进行独立标定，而不是为平滑训练曲线偷偷修改。

## 5. 实际修复与版本边界

新增：

- `sustained_cohort_protocol.py`：**可选择**使用更真实的 20s/30s warm-up，只模拟更长的过去请求与队列历史；原始时延 Reward、8s 尾部、请求分布和调度器保持一致；6s 与历史精确同值。**这是一项评价修复，不是完整长期仿真。**
- `versioned_edit_rollout.py` 增加 `warmup_seconds` 参数，默认仍为 6；未改动历史 `edit_policy_study.py`。
- `cpu_viability_contract.py`：全局 LP 只读报告；**没有 CPU 硬掩码、人工副本配额、候选完整布局池、Reward 筛选/替换、事后矩阵投影。**
- 原始 192 矩阵独立 LP 审计、同请求预热因果干预、120s 压力评价及双种子训练对照均有源码、原始记录和图。

**为什么没有直接把 `rho >= 1` 变成 FINISH 硬掩码？** 需要先定义长周期平均需求、网络资源和可靠性合同；同时，要验证任何部分部署是否还存在可通过继续 ADD/RELOCATE 走到合法终止的路径，避免强制策略陷入无 FINISH 的死循环。`rho < 1` 仍不充分，靠这一项硬掩码无法覆盖所有链路/调度风险。下一轮应研究物理可达性与 CMDP 约束，而不是增加任意配额或强制修改 Agent 输出。

## 7. 下一阶段必须解决的问题

1. **先签订物理可行性合同**：结构合法（覆盖/RAM/SSD）与运行可持续（CPU/链路/调度服务质量）分层，明确持续服务强度和统计 SLA；不要把合法内存部署等价于可服务部署。
2. **在不限制副本数量、不造候选部署池的条件下设计可终止的资源约束构造策略**：检查部分构造状态未来是否可达安全完整部署；否则若只在 FINISH 硬掩码 CPU 约束，会让 Actor 无法结束。
3. **把单步差异产生的真实长期瓶颈反馈正确用于 Actor**：区分可持续/暂时性尾延迟、更新样本中极端优势对梯度的主导；不修改原始 Reward，可另行使用方差控制但必须报告策略学习曲线。
4. **训练与验证统一采用长期可信度标准**：20s warm 是低成本改进但未必够；使用 D120 流作为独立压力审计、跨人口/跨场景随机化、真实失败/截尾分列。仅 4 次更新不够收敛验收。
5. **资源模型合同另行确认**：当前总 CPU 366.9 CU/s、AP 60.7–118 Mbps、CPU `finish_pf`、无独立 NIC 总量约束，与最初 7200 CU/s、每 AP 300 Mbps、CPU 平方根 KKT 不一致；禁止和 Actor 算法修复一起悄悄重标定。
