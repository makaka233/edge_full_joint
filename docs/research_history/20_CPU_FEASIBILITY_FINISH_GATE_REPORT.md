# Agent-D：CPU 可持续承载 FINISH 约束与策略学习双种子验证（2026-11-19）

## 结论

- **当前 EDIT 策略确实允许 ADD、REMOVE、RELOCATE、FINISH**。覆盖阶段只能 ADD；覆盖完成后才允许全部编辑动作。
- **已完成真实代码改动**：在 `versioned_edit_rollout.py` 中增加可选 `cpu_finish_guard`；完整草稿的理想 CPU 最小最大负载下界 `rho* >= 1` 时，暂时禁止 FINISH；仍由 Actor 在全部合法编辑中自主采样。`rho* < 1` 后恢复 FINISH。没有投影、人工副本上限、额外候选完整矩阵、Reward 裁剪、事后替换或强制终止。
- **双种子真实物理短训结果支持修复有效性，但不支持宣称 RL 收敛**：双种子、每种子 4 次 Actor 更新、每组每种子 12 条训练物理轨迹；组间同样的请求随机数与保持一致的环境资源配置；独立 Holdout 每组每种子 12 条（0/2/4 更新各 4 条）。约束组 24/24 训练+24/24 Holdout 均自然 FINISH，且 CPU 必要条件通过；基线训练 7/24 张 `rho* >=1`，Holdout 7/24 张。
- **最重要的限定**：约束组在更新 0 就明显比原组好，收益很大部分来自纠正可提交动作空间，不是因为网络通过 4 次更新学会了高水平部署。
- **尚未证明**：所有初始草稿均有有限动作安全完成路径；`rho*<1` 是真实稳定、低时延充分条件；长期 120 秒/多周期 KEEP/BUILD 与 Agent-S 联合训练已通过；资源总量/CPU 分配器已和最早研究合同一致。

## 1. 当前实际动作语义（核对源码）

`edit_policy_study.py` 中：`e.phase==1` 只选择阶段覆盖 ADD，缺一个阶段的最后副本不允许删除；`e.phase==2` 则选择 `P(FINISH)` 或 `P(CONTINUE)*P(kind|CONTINUE)*P(edit|kind)`，编辑操作有 `ADD`、`REMOVE`、`RELOCATE`。`native_legal_edit_prototype.py` 对每个操作先检查 RAM/SSD 和覆盖，RELOCATE 原子执行。`ADD_ONLY` 是历史对照分支而非现阶段编辑策略。每个内部动作不推进物理时间，完整矩阵只在 FINISH 后提交一次。当前实验 BUILD-only，不代表多周期跨部署迁移已证明。

## 2. 安全终止数学定义和限制

部署矩阵为 `X in {0,1}^{28x32}`，设各阶段平均计算需求 `D_k`，节点计算容量 `C_n`。计算：

`rho*(X) = min_{z>=0,rho} rho`, subject to `sum_{n:X[k,n]=1} z[k,n] = D_k`, `sum_k z[k,n] <= rho C_n`。

在当前稳态平均需求、理想可分配资源模型下 `rho* >=1` 表示不可持续承载（必要条件不满足）；`rho* <1` 只表示 CPU 必要条件不被否定，**不保证**真实调度、网络、无线、排队、峰值需求或 SLA。

修改严格是 **FINISH 动作合法集**，不是 Action 评分奖励，也不是事后改部署矩阵。若 `FINISH` 被屏蔽，继续动作的条件分布从 `log P(continue)+log P(edit|continue)` 变为 `log P(edit|continue)`；熵也按条件编辑动作重算。`test_cpu_viable_finish_policy.py` 的梯度测试证实屏蔽时不存在多余 FINISH 头梯度。

限制：现有代码没有数学上证明任意结构合法草稿都能经过有限编辑达到 `rho*<1`。因此若上限 1100 步仍不能 FINISH，报告不可终止失败，不制造一个物理 Reward，也不自动强制提交。试验中所有目标样本自然结束，不是普适可终止性定理。

## 4. 因果与负结果边界

这组结果强烈支持原环境存在 **可提交动作空间过宽** 的工程缺陷：在 28×32 的规模上，覆盖+RAM/SSD 不能代替可持续服务必要条件。CPU 不可持续部署被原 FINISH 接受、短窗又可能漏报积压，造成 Reward 随选择的矩阵突变；仅增强 Actor/Critic 很难解决动作本身物理语义错误。

CPU 终止约束也改变了策略行走长度，新增一些 REMOVE / RELOCATE 行为并没有被人为禁用或选优。`rho*<1` 布局仍可能有链路拥塞、S 调度、峰值负载问题，不能报告“全部尖峰彻底消除”。强制 FINISH 屏蔽还可能在资源不足的草稿中产生很长的编辑路径甚至非终止；需要专门研究**安全可达性**与 **有限时间退出或返回 KEEP** 的真实合同，不能由实验中的 0 非终止直接推定永远安全。

## 6. 下一步必须正视的问题

1. 在多个独立资源/需求状态上验证是否存在结构合法但无法通过 ADD/REMOVE/RELOCATE 达到 `rho*<1` 的构造死局；不允许隐藏掉非终止轨迹。
2. 理想 CPU 约束只保证**必要条件**。用连续 120 秒和更多独立用户人口验证在 `rho*<1` 内能否仍出现尖峰，找出链路、调度、尾部截尾和峰值负载分量。
3. 从随机初始化训练至少更长的单种子/双种子，持续记录非平滑物理 Reward、E2E 和失败率，评价策略内部是否改善而不只是刚初始化就因掩码改善。
4. 如需真正的有约束 MDP，可设计安全可达动作的学习表示、包含风险约束的值函数以及可能的安全回退到已有部署，但不能用事后投影替换 Actor 行为，也不能把任意阈值伪装成物理定律。
5. 单独确认最初物理合同与当前实际运行环境 CPU 366.92 CU/s、AP 60.71–118.07 Mbps、`finish_pf` 的差异，禁止与本轮算法修复一起静默重标定。
